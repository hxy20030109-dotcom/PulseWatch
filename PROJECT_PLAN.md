# PulseWatch Project Plan

## Objective

Build a reproducible predictive-maintenance prototype and a small service
around it. Demonstrate sound classification under class imbalance, responsible
threshold selection, and basic model/service monitoring.

## Intended audience

Applied ML, machine-learning engineering, and software engineering internship
roles. The project complements VisionSeek's retrieval/ranking focus with a
tabular ML workflow and deployable inference service.

## Research questions

1. How do a calibrated linear baseline and a tree ensemble compare on
   precision-recall trade-offs?
2. How does the selected alert threshold change false-negative and
   false-positive counts?
3. Can the monitoring demo distinguish input drift from measured model-quality
   degradation when labels become available?

## Data and limitations

- Dataset: UCI AI4I 2020 Predictive Maintenance Dataset (10,000 records).
- UCI describes the dataset as synthetic and licenses it CC BY 4.0.
- The initial task is per-record failure classification, not remaining-useful-
  life prediction for an individual machine.
- Row order is used for a chronological robustness split, but the dataset does
  not provide a validated deployment timeline or production machine identity.
- No real-world performance claim will be made from this dataset.

## Version 1 scope

### Modeling

- Validate expected columns, types, target values, and row identifiers.
- Exclude identifiers (`UDI`, `Product ID`) and failure-mode labels (`TWF`,
  `HDF`, `PWF`, `OSF`, `RNF`) from features.
- Use ordered train/validation/test partitions; fit preprocessing only on train.
- Compare Logistic Regression and Random Forest baselines.
- Select an alert threshold on validation data using an explicit operating
  objective; freeze it before evaluating test data.
- Report PR-AUC, precision, recall, F2, confusion counts, and alert rate.

### Service and monitoring

- Expose a versioned prediction endpoint with input validation.
- Log model version, request outcome, latency, and risk score without storing
  unnecessary personal data.
- Simulate batches and controlled feature-distribution shifts.
- Report drift separately from quality metrics, which require ground-truth
  labels.
- Package a local demo with Docker and document one-command startup.

## Acceptance criteria

- A new user can prepare the dataset and reproduce both baseline reports.
- The test set is not used for feature selection, threshold choice, or model
  selection.
- All reported metrics are generated by the committed code and config.
- The API rejects malformed input and returns model/version metadata.
- A demo shows a normal batch and a controlled shifted batch, with drift
  alerts clearly distinguished from proven performance degradation.
- README documents provenance, limitations, architecture, and reproducibility.

## Out of scope

- Claims of industrial deployment or real factory accuracy.
- Deep sequence models on a dataset without reliable per-machine time series.
- Kubernetes, cloud infrastructure, or a large frontend before the local
  pipeline and measurements are sound.
- Automatic retraining without a reviewable validation and release gate.
